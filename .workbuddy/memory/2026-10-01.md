## 智能调度被打断后恢复时补一次扫图

需求：智能调度（OpsiScheduling）运行途中被 `check_task_switch` 插入其它任务（任务切换 → TaskEnd），
等那个任务跑完、调度重新进入时，在第一次练级/短猫回到打捞海域后**多扫一次图**（`map_rescan(full)`），
防止离开期间刷出来的地图事件被漏掉。

实现（4 个文件）：
1. `module/os/tasks/scheduling.py` —— 用 `OpsiScheduling.Storage.Storage` 的 `SchedulingInterrupted`
   字段记「上次是否被任务切换打断」。进入时先读标记决定 `self._resume_extra_scan`，再置 True；
   正常退出（`wait` / 子任务禁用 / 探索中）清 False，`check_task_switch` 打断时保留。
2. `module/os/map.py` —— `OSMap.consume_resume_extra_scan()`：消耗 `_resume_extra_scan`，做一次 full 扫图。
3. `module/os/tasks/hazard_leveling.py` / `meowfficer_farming.py` —— `globe_goto` + `fleet_set` 之后调用它。
4. 新增 `tests/os/test_scheduling_resume.py`（6 条单测，全绿）。

跑测试仍用运行实例的 `toolkit/python.exe`（3.7.6），cwd 仓库根，手写 runner。
回归：`test_fixed_patrol.py` 16 条全绿；`test_coin_thresholds.py` 仍只有既有 3 条失败（与本次无关）。
注意：`scheduling.py` 是 CRLF 行尾，另三个文件是 LF；Edit 时保持各自行尾一致即可。

待办：这 4 个文件 + 新测试文件也要同步到运行实例才生效。

补充确认（用户后续澄清）：「扫图」= `map_rescan(full)`，它要完成的是三件事——地图事件（探索容器/探索奖励）、
明石商店（`is_akashi`）、两种塞壬装置（`is_scanning_device` 塞壬扫描装置 + `is_logging_tower` 塞壬灯塔）。
这些都在 `map_rescan_current` 里按优先级逐个处理，与 `map_rescan` 的 docstring 一致。
注意点：非探索任务（智能调度属于这种）里 `map_rescan` 每轮只清一个事件（`not is_in_task_explore and len(_solved_map_event)` 提前停），
所以一次恢复扫图最多补一个，其余留给后续练级轮次。
另修一处隐患：`consume_resume_extra_scan` 调 `map_rescan` 前要先 `self._solved_map_event = set()` / `_solved_fleet_mechanism = False`，
否则可能改到类级共享 set，跨实例串状态（与 `run_auto_search`/`run_strategic_search` 的既有写法对齐）。

## 任务抢占后的地图状态恢复（Resume Barrier，第四次）

需求：Opsi 任务被其它任务抢占、再回来时，不能继续信任抢占前的地图缓存，必须 FULL RESCAN + 失效旧状态。

根因（先调查后动手）：
1. fork 的 `os_init()` 是**每次 Opsi 任务进入都执行**的入口（`load_campaign` → `merge` 返回同一个 config 对象 → `os_init`），
   里面 `# self.map_init()` 被注释掉，`run_auto_search(rescan=False)` 也不做 full 扫图——所以「恢复」时没有显式的重扫屏障。
2. 抢占点是 `AzurLaneConfig.task_switched()`（`check_task_switch` → `task_stop` 抛 TaskEnd）；正常结束走 `task_stop()` 不经过它。
   区分「被抢占」和「正常结束」的关键就在这个函数：`prev != new` 且 `prev.command` 是 Opsi 开头。
3. 关键约束：`alas.py` 每次任务成功后 `del_cached_property(config)` 重建 config 对象（从文件读），
   所以 stale 标记必须**写进 config 文件**（cross_set → update → save），不能只存内存。

改动：
- `module/config/config.py`：新增常量 `OS_MAP_STALE_KEY = 'Alas.Storage.Storage.OpsiMapStale'`；
  `task_switched()` 在 `prev != new` 且 `prev.command.startswith('Opsi')` 时 `cross_set(OS_MAP_STALE_KEY, True)`。
- `module/os/map.py`：`OSMap` 新增 `_os_map_was_interrupted()` / `_handle_os_resume()`（resume barrier：失效 `_solved_map_event`/`_solved_fleet_mechanism` + `map_rescan(full)` + 清标记 + 日志），
  `os_init()` 在 `zone_init`/`handle_after_auto_search` 之后、特殊海域判断之前调用。
- 新增 `tests/os/test_os_resume.py`（7 条，全绿）。

要点：
- 只按「生命周期」触发，不按循环触发：标记在 task_switched 置 True，resume barrier 置 False，一次抢占只扫一次。
- 连续两次抢占 = 两次独立 interrupt → 各扫一次（每次 task_switched 都会重新置 True）。
- 与上一轮 `SchedulingInterrupted`/`_resume_extra_scan`（OpsiScheduling 专属，第一轮练级多扫）**并存但不冲突**：
  `_handle_os_resume` 扫的是 os_init 时所在的当前海域（可能是港口 → map_rescan 直接 return False），
  `_resume_extra_scan` 扫的是 `globe_goto` 后的打捞海域，两者目标海域通常不同，属于互补。
- 恢复时页面/海域确认由 `os_init` 既有的 UI 切换 + `zone_init()` 承担；`map_rescan` 自带 `zone.is_port` 守卫。

测试回归（toolkit/python.exe 3.7.6）：`test_os_resume.py` 7 全绿、`test_fixed_patrol.py` 16、`test_fixed_patrol_target.py` 16、
`test_scheduling_resume.py` 7 全绿；`test_coin_thresholds.py` 仍只有既有 3 条失败（与本轮无关）。
