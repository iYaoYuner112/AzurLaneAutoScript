## 石油购买行动力被行动力箱抢占（第三十六次）

用户报：大世界设置里的「买行动力 X 次」不生效，因为运行时优先用行动力箱。

根因：本仓库自己加的 commit `4e677464c 行动力箱使用优化` 在 `handle_action_point` 的
「current >= cost」分支里插了一段「用箱把当前行动力补到上限」。于是只要行动力够，
就先开箱补到 200 → current 永远 ≥ cost → 下面那段「买行动力」永远不会被走到。
（AP 的 handle_action_point 根本没有这个分支：够用就开工，不足才买油，最后才开箱。）

修复（module/os_handler/action_point.py）：
1. 补箱分支增加条件 `OpsiGeneral_BuyActionPointLimit <= 0`：玩家配了买油就只用油，
   没配买油才保留补箱优化。顺序变成「够用→开工 / 不足→先买油→再开箱」。
2. 末尾没有可用箱子时区分日志：箱还在但开箱会超 200 → `Opening any box would exceed 200 current action points, wait for natural recovery`（原来一律说 No more action point boxes，误导）。

确认过 action_point_set 是唯一入口，没有别的先开箱路径；action_point_buy 只在 current < cost 时调用。

测试：tests/os/test_action_point_priority.py 新增 3 例（买油开启不补箱 / 未开启仍补箱 100→200 用 5 个蓝箱 / 非智能调度任务不补箱），
os 回归 87/87 全绿。

同步：module/os_handler/action_point.py 已覆盖实例并 md5 校验，旧文件备份 `action_point.py.bak-20261003`；需重启 ALAS 生效。

## 更正：我们仓库没有 AP 的防溢出那套（说明性，无代码改动）

我在汇报里说过「avoid_ap_overflow 这个在我们仓库里有自己的防溢出实现（OpsiPreventActionPointOverflow 那条线）」——**说错了**，向用户更正。

实测（grep module/ 全库）：
- 我们仓库**没有** `OpsiPreventActionPointOverflow`（那是 AP 的 module/os/tasks/prevent_action_point_overflow.py，一个独立任务：行动力快顶到 200 时代跑调度把行动力花掉）
- 我们仓库**没有** `avoid_ap_overflow`（那是 AP handle_action_point/action_point_set 的参数，侵蚀1专用：
  current >= ACTION_POINT_AVOID_OVERFLOW_START(100) 就直接开工不等不买不开箱；低于 100 时跳过「开完会 >=200」的箱子。
  AP 侵蚀1用 action_point_set(cost=120, avoid_ap_overflow=True)，另有 action_point_reusable() 复用读数）
- 我们这边跟行动力上限沾边的只有两条，方向还与 AP 相反：
  `action_point.py:167 if total > 3000: override(DoRandomMapEvent=False)` 和
  `hazard_leveling.py:60 if _action_point_total >= 3000 and not smart_scheduling: 让路`（囤太多就别练了），
  其余都是「保留行动力（OS_ACTION_POINT_PRESERVE / ActionPointLimit）」= 省着用。

结论：单独搬 avoid_ap_overflow 对我们**零效果**——我们侵蚀1的 cost=70 < 100，循环第一个分支 current>=cost 永远先命中，
第 100 行开工线和「避开顶到 200 的箱」都走不到。要真正对齐得连 AP 的 cost=120 语义和 action_point_reusable 一起改
（那会改变侵蚀1的开工线）。已把选择权交回用户，暂不动代码。
